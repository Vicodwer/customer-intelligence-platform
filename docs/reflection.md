# Reflection

## What was built

This project built a Customer Intelligence Platform with two intelligence lanes:

1. A campaign conversion prediction service.
2. A complaint intelligence service with retrieved evidence IDs.

The final system includes data ingestion, validation, feature engineering, model training, model evaluation, RAG retrieval, grounded complaint answers, monitoring, CI, Docker, and FastAPI endpoints.

---

## What worked well

The script-first design made the project reproducible and CI-friendly. Each major capability can be run independently:

```text
ingest
validate
features
train
evaluate
build RAG index
run RAG evaluation
serve API

The API layer became a unified product interface, not just separate ML and RAG demos. The /customer-intel endpoint combines conversion scoring with complaint intelligence.

GitHub Actions helped catch missing tracked folders and verified the full pipeline from a clean environment.

Docker made it possible to run the API from source without relying on local artifacts.

Key technical decisions
Dropping duration

The duration column was excluded from ML features because it is only known after a campaign call ends. Keeping it would create train-serving leakage.

Promotion gate

The model promotion gate prevents blindly replacing the baseline. It compares PR-AUC, F1, and ROC-AUC and demonstrates governance by blocking a deliberately worse dummy model.

TF-IDF RAG MVP

TF-IDF retrieval was selected for the MVP because it is deterministic, lightweight, and CI-friendly. This made it easier to test evidence retrieval and refusal behavior.

Deterministic complaint answers

The complaint answer generator summarizes retrieved records deterministically instead of using a generative LLM. This reduces hallucination risk and makes citation behavior testable.

Main challenges

The biggest challenges were operational:

Dataset download failures.
SSL and API endpoint issues.
Empty Git folders not being tracked.
Docker context initially being too large.
Port conflicts when running Docker and local API together.

Each issue was fixed by making the system more robust:

fallback ingestion paths
.gitkeep files
improved .dockerignore
alternate Docker port mapping
CI validation
Current limitations
The RAG system uses TF-IDF instead of dense embeddings.
The complaint answer is deterministic, not generated by an LLM.
Docker startup retrains and rebuilds artifacts, which is reproducible but slower than a production image.
No cloud deployment is included yet.
No auth, rate limiting, or production observability stack is included.
No SHAP or detailed model explainability dashboard is included.
What I would improve next
Replace TF-IDF with sentence-transformer embeddings and FAISS or Chroma.
Add a true LLM synthesis step with strict citation grounding.
Add SHAP or permutation importance for model explainability.
Add Azure deployment.
Add structured request logging.
Add latency dashboards and alerting.
Add an artifact registry or model registry.
Add authentication and rate limiting.
Split Docker image build from runtime startup to avoid retraining on each container start.
